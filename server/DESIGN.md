# Spend Tracker Design

A simple expense tracker with APIs to add an expense, list expenses with category and date filters, and a summary endpoint that shows total spend, spend by category and month over month change for one month.

## 1. Scope

### Must

- 3 endpoints
    - `POST /expenses` - add an expense
    - `GET /expenses` - list expenses, filter by category and date range
    - `GET /summary` - total, spend by category and month over month change
- Minimal UI
    - Add an expense
    - Show recent expenses and the summary

### Bonus

- API key auth (single user)
- Deployed to Render
- Flag a category when its spend increases more than 20% vs the previous month

### Out of scope

- JWT / multi user
- Edit and delete expenses
- Multiple currencies

### Assumptions

- Single user
- INR only
- "Current month" is decided in IST (Asia/Kolkata), not the server clock

## 2. Data Model

```
Table: expenses

- id            TEXT(36)   PRIMARY KEY     UUID4, generated by the app
- amount_paise  INTEGER    NOT NULL        CHECK (amount_paise > 0)
- category      TEXT       NOT NULL        trimmed + lowercased before insert
- note          TEXT       NULL
- spent_on      DATE       NOT NULL        stored as ISO text (YYYY-MM-DD)
- created_at    DATETIME   NOT NULL        UTC

Indexes:
- ix_expenses_spent_on            (spent_on)
- ix_expenses_category_spent_on   (category, spent_on)
```

Why:
- `amount_paise` is an integer. Floats can't store some decimals exactly (0.1 + 0.2 != 0.3), and SQLite has no exact decimal type. Rs 250.50 is stored as 25050.
- `spent_on` is a date, not a datetime. The user logs the day they spent. ISO text sorts in date order, so range filters work on text in SQLite.
- The `(category, spent_on)` index covers "category + date range" filters. The `spent_on` index covers date-only filters and the monthly summary.
- UUID instead of an auto-increment id, so the API doesn't reveal how many rows exist.
- The CHECK constraint is a second guard. Pydantic validates the API, the DB protects the data.

## 3. API Contract

All endpoints except `/health` and the UI need the header `X-API-Key`.
Money goes in and out as a string with 2 decimals. Dates are `YYYY-MM-DD`.

### `POST /expenses`

Request:
```json
{
    "amount": "250.50",
    "category": "Food ",
    "note": "lunch",
    "spent_on": "2026-09-21"
}
```

Rules:
- `amount`: string, > 0, max 2 decimals, max 15 rupee digits (stays inside SQLite's 64 bit integer). A JSON number is rejected, because it is already a float when it is parsed.
- `category`: trimmed, lowercased, 1-50 chars.
- `note`: optional, max 500 chars.
- `spent_on`: exactly `YYYY-MM-DD` and a real calendar date.
- Unknown fields are rejected.

`201`:
```json
{
    "id": "008b002d-0403-44e2-bf75-0272b012fce0",
    "amount": "250.50",
    "category": "food",
    "note": "lunch",
    "spent_on": "2026-09-21",
    "created_at": "2026-09-22T14:15:33.050328Z"
}
```

The full expense is returned, so the client doesn't need a second call.

### `GET /expenses`

Filters are query params, not a JSON body. Browsers don't send a body with GET.

```
GET /expenses?category=food&category=medicine&date_from=2026-09-01&date_to=2026-09-10&limit=50&offset=0
```

Rules:
- `category` can repeat. It is normalised the same way as on create, so `Food` matches `food`.
- `date_from` and `date_to` are inclusive. Either one can be sent alone.
- `date_from > date_to` -> 422.
- `limit` 1-100 (default 50), `offset` >= 0.
- Unknown params -> 422, so a typo like `?categroy=food` fails instead of returning everything.
- Sorted by `spent_on DESC, id DESC`. The id breaks ties so pages don't overlap.

`200`:
```json
{
    "expenses": [
        {
            "id": "008b002d-0403-44e2-bf75-0272b012fce0",
            "amount": "250.50",
            "category": "food",
            "note": "lunch",
            "spent_on": "2026-09-21",
            "created_at": "2026-09-22T14:15:33.050328Z"
        }
    ]
}
```

### `GET /summary`

```
GET /summary?month=2026-09
```

`month` is optional. Default is the current month in IST.

`200`:
```json
{
    "month": "2026-09",
    "is_partial_month": true,
    "total": "10100.00",
    "previous_month": { "month": "2026-08", "total": "10000.00" },
    "mom_change": { "amount": "100.00", "percent": 1.0 },
    "by_category": [
        { "category": "food", "total": "5200.00", "previous_total": "5000.00",
          "change_percent": 4.0, "flagged": false },
        { "category": "travel", "total": "4100.00", "previous_total": "3000.00",
          "change_percent": 36.67, "flagged": true }
    ]
}
```

### Errors

- `422` - bad input. FastAPI's standard shape, one entry per bad field:
  ```json
  {"detail": [{"loc": ["body", "amount"], "msg": "Value error, amount must be greater than 0", "type": "value_error"}]}
  ```
- `401` - missing or wrong API key. Both give the same response, so a caller can't tell which one it was:
  ```json
  {"detail": "Invalid or missing API key"}
  ```

## 4. Summary Rules

- **Total** = spend in the chosen month. Not all time, so it matches the month over month numbers.
- **Month range** is half open: `spent_on >= '2026-09-01' AND spent_on < '2026-10-01'`. No `strftime()` on the column, so the index is used.
- **Previous month** of `2026-01` is `2025-12`.
- **MoM amount** = current - previous.
- **MoM percent** = (current - previous) / previous * 100, rounded to 2 decimals. Rounding is done with integers, so a float can't round a .xx5 value the wrong way.
- **Previous month = 0** -> percent is `null`. 0% and infinity would both be wrong.
- **Categories** = union of both months. A category only in the previous month shows `0.00` now and -100%.
- **Flag** when `previous > 0` and `current * 100 > previous * 120`. Integer maths. Exactly +20% is not flagged, the spec says "more than 20%". A new category (previous = 0) is not flagged.
- **is_partial_month** = the month contains today. It tells the user that "down 40%" on the 5th is not final.
- Totals come from SQL (`SUM ... GROUP BY category`), one query per month. The maths is in pure functions in `summary.py` (no DB, no clock), so it is unit tested directly.

## 5. Edge Cases

`POST /expenses`
- amount missing, `"0"`, `"-5"`, `"abc"`, `"1.234"`, a JSON number, too many digits -> 422
- category missing, `""`, `"   "`, over 50 chars -> 422
- `"Food "` -> stored as `food`
- note over 500 chars -> 422, `null` is fine
- date missing, `"2026-02-30"`, `"21-09-2026"`, `"20260921"` -> 422
- extra field -> 422
- `"0.10"` + `"0.20"` sums to exactly `"0.30"`

`GET /expenses`
- no filters -> all rows, paginated
- expense on exactly `date_to` -> included
- `date_from > date_to` -> 422
- unknown category -> `[]`
- limit 0, -1, 101 -> 422
- unknown query param -> 422

`GET /summary`
- empty DB -> totals `0.00`, percent `null`
- `month=2026-13`, `month=abc` -> 422
- previous month 0 -> percent `null`
- spend dropped -> negative change
- exactly +20% -> not flagged, just above -> flagged
- `month=2026-01` compares with `2025-12`

Auth
- missing key, wrong key -> 401
- `/health` and the UI work without a key

## 6. Decisions

- **Money:** float / Decimal / int paise -> **int paise**. Floats drift, SQLite has no exact decimal.
- **Amount in the API:** number / string -> **string**. A JSON number is a float before my code sees it.
- **Date format:** DD-MM-YYYY / ISO -> **ISO**. Sorts correctly as text, standard.
- **Filters:** GET body / query params -> **query params**. GET bodies aren't supported by browsers.
- **Summary scope:** all time / one month -> **one month**. Consistent with MoM.
- **Default month timezone:** UTC / IST -> **IST**. Users are in India, the server runs in UTC.
- **MoM % when previous = 0:** 0 / infinity / null -> **null**.
- **Category:** enum / free text / normalised text -> **normalised text**. Flexible, and no split totals.
- **Aggregation:** Python loop / SQL -> **SQL GROUP BY**.
- **Pagination:** none / offset / cursor -> **offset**, capped at 100. Enough for this size.
- **ID:** integer / UUID -> **UUID**. Doesn't expose row count.
- **Auth:** none / API key / JWT -> **API key**. Single user.
- **UI:** React / plain HTML -> **plain HTML served by FastAPI**. Same origin, so no CORS and no build step.
- **Hosting:** Render / Vercel -> **Render**. One long running process fits SQLite. Vercel is serverless and each instance has its own temp disk.
